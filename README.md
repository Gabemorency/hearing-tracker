# hearing-tracker

A live tracker for U.S. Senate and House committee hearings, plus a directory of
current members of Congress. Served as a static site via GitHub Pages — there is
no application server; all data is produced by scheduled GitHub Actions that
scrape public sources and commit the results straight to `main`.

## Site

- `index.html` — today's hearings across House and Senate committees, refreshed every 2 hours.
- `calendar.html` — day-by-day hearing history and House in-session status, plus the
  upcoming schedule.
- `members.html` / `bios/*.html` — member directory with per-member bio pages.
- `manifest.json`, `sw.js`, `offline.html` — PWA/offline support.

## Data pipeline (GitHub Actions)

| Workflow | Schedule | What it does |
|---|---|---|
| `update.yml` | every 2 hours | Runs `scrape.py` (Playwright) against committee pages, merges into `snapshot.json`, pulls DomeWatch floor data, records today's status in `calendar_history.json` (`record_calendar_day.py`), rebuilds `index.html`. |
| `nightly.yml` | weeknights, 9pm ET | Runs `build_baseline.py` (tomorrow's schedule) and `build_members.py` (full member directory + bio pages), rebuilds `calendar.html`/`members.html`. |
| `domewatch_calendar.yml` | twice daily, ~9pm & ~9am ET | Runs `fetch_domewatch_calendar.py` (Playwright, against domewatch.us/calendar) to capture the next ~5 months of DomeWatch's projected Voting Day / holiday calendar into `domewatch_calendar.json`. |
| `bio_sync.yml` | every 6 hours | Detects new/departed members against `unitedstates/congress-legislators`, calls an LLM API to write bios for new members, updates `bios_hardcoded.json`. |
| `generate_bios.yml` | manual only | One-time/bulk regeneration of all member bios via an LLM API. |
| `validate.yml` | every 3 days | Sanity-checks hardcoded data (institutional leadership, CBC roster, vacant seats) against live sources; opens a GitHub issue on drift. |
| `tests.yml` | every push/PR | Runs the pytest smoke tests in `tests/`. |

`scrape.py` and `build_baseline.py` scrape committee pages directly (Playwright +
BeautifulSoup/pdfplumber for witness-list PDFs). `build_members.py` and
`bio_sync.py`/`generate_bios.py` pull structured data from the
[unitedstates/congress-legislators](https://github.com/unitedstates/congress-legislators)
project rather than scraping.

`baseline.json` is the source of truth for "what hearings are scheduled" —
`scrape.py` only enriches it (room changes, witness lists, cancellations) and
never overwrites baseline entries wholesale, so a bad scrape can't silently
delete a real hearing.

## Data files

- `bios_hardcoded.json` — member bio text, keyed by bioguide ID. Written by
  `bio_sync.py`/`generate_bios.py`, read by `build_members.py`. Plain JSON
  (not committed as Python source) so diffs stay readable and the file has no
  import-time side effects.
- `members.json` / `baseline.json` / `domewatch_*.json` — generated data,
  regenerated by their respective workflows. Don't hand-edit; changes will be
  overwritten on the next run.
- `calendar_history.json` — day-by-day archive keyed by ISO date
  (`{"2026-07-28": {"hearings": [...], "inSession": true}}`), read by
  `calendar.html`. Appended to once per day by `record_calendar_day.py`
  (`update.yml`) — an existing day's entry is only touched again while it's
  still "today"; once the day rolls over that entry is final and earlier
  days are never rewritten.
- `institutional_leadership.json` / `vacant_seats.json` — the one genuinely
  hand-maintained data in the repo (leadership elections and new vacancies
  aren't published anywhere machine-readable). `build_members.py`,
  `generate_bios.py`, and `validate_hardcoded.py` all read the same files so
  they can't drift out of sync. `validate_hardcoded.py` auto-removes a
  vacant-seat entry once that district has a sitting member again, but can't
  auto-add a *new* vacancy or a leadership change — it opens a GitHub Issue
  for those instead.

## Tests

`tests/` has pytest smoke tests for the pure parsing/formatting/matching
logic — no network calls, no browser, nothing that touches a live site.
They exist to catch regressions in the functions most likely to break
silently when a source site's markup changes or a helper gets refactored:

- `tests/test_scrape.py` — the `scrape.py` helpers: committee-name
  normalization (`norm_cmte`), fuzzy-matching two hearings as the same event
  from different sources (`fuzzy_match`, `cmte_similarity`), witness-list and
  chair extraction from raw scraped text, room-to-building mapping, the
  day-over-day diff that powers the "⚡ Updated" change pills
  (`diff_hearing`), and `watch_link` (matching a hearing to its committee's
  real hearings page).
- `tests/test_build_members.py` — the `build_members.py` formatting helpers:
  initials, party label/class, photo URL construction, and institutional
  leadership title matching.
- `tests/conftest.py` — just puts the repo root on `sys.path` so the tests
  can `import scrape` / `import build_members` directly.

What this does **not** cover: the actual scraping (real requests against
docs.house.gov/senate.gov/congress.gov — those only run for real inside
`update.yml`/`nightly.yml`), the generated HTML/JS in the browser, or the
GitHub Actions workflows themselves. A green test run means the parsing
logic is sound, not that the live site is rendering correctly.

`tests.yml` runs the full suite on every push and pull request. Run it
locally with:

```
pip install pytest playwright beautifulsoup4 lxml pdfplumber requests pyyaml
python -m pytest tests/ -v
```
